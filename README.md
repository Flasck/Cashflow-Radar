# CashFlow Radar

Приложение для фактических денежных операций нескольких компаний и точечного прогноза дневного NetCF. Учебная реализация, не банковская система и не доказанный результат НИР.

Текущий объём — **ЛР1–3**. Docker используется как удобный способ запуска.

## Запуск на Windows

Нужен работающий Docker Desktop. Из корня проекта:

```powershell
.\scripts\start-local.ps1
```

Открыть `http://localhost:3000`, зарегистрироваться и создать компанию. API/Swagger: `http://localhost:8000/docs`. Секреты создаются один раз в `.env`, файл игнорируется Git. Не публикуйте его. `init-local.ps1` генерирует реальные секреты и не перезаписывает существующий `.env`.

Это основной Compose проекта. После создания `.env` доступны стандартные команды из корня:

```powershell
docker compose up --build -d --wait
docker compose ps
docker compose logs -f
docker compose stop
```

Остановка без удаления данных:

```powershell
.\scripts\stop-local.ps1
```

Основной файл — **`compose.yaml`**, Compose project — **`cashflow-radar`**. Для новой установки БД называется `cashflow_radar`, volume — `cashflow-radar_postgres`. Существующая установка подключает прежние БД/volume через `RADAR_DB_NAME`, `RADAR_POSTGRES_VOLUME` и `RADAR_POSTGRES_EXTERNAL=true` в локальном `.env`: данные и секреты при смене имени проекта не пересоздаются. Внешний volume должен существовать заранее; для новой установки оставьте `RADAR_POSTGRES_EXTERNAL=false`. Не использовать `down -v` для обычной остановки.

| Сервис | Контейнер | Назначение |
|---|---|---|
| `frontend` | `cashflow-radar-frontend-1` | Next.js standalone, `127.0.0.1:3000` |
| `api` | `cashflow-radar-api-1` | FastAPI, `127.0.0.1:8000` |
| `forecast` | `cashflow-radar-forecast-1` | gRPC Engine, только внутренняя сеть |
| `postgres` | `cashflow-radar-postgres-1` | PostgreSQL 16, `127.0.0.1:55432` для локальных инструментов |
| `migrate` | `cashflow-radar-migrate-1` | Одноразовый `alembic upgrade head`, тот же образ, что у API |

Порядок запуска: готовая БД → успешная миграция → API → frontend; Engine запускается перед API. Healthchecks оставлены только у БД и API: миграция ждёт подключений к PostgreSQL, frontend — ответа API. Для Engine и frontend проверяется запуск контейнера, а не готовность приложения. Статус `Exited (0)` у миграции нормален. Автоматических перезапусков и дополнительных production-настроек в Compose нет. Прикладные процессы по-прежнему работают не от root (это задано в Dockerfile). Секреты и локальные окружения исключены из Docker build context.

Основные поля Compose:

- `image` — используемый образ; `build` — откуда его собрать.
- `environment` — настройки приложения; `${...}` подставляет значения из `.env`.
- `ports` — порт компьютера слева, порт контейнера справа.
- `volumes` — постоянное хранилище PostgreSQL, отдельное от контейнера.
- `depends_on` — порядок запуска; `healthcheck` — проверка готовности.
- `command` — команда контейнера; у `migrate` она запускает Alembic вместо API.

## Подтверждение почты

Регистрация отправляет шестизначный код на email. До подтверждения аккаунт не может войти; после правильного кода устанавливаются cookies входа. Код действует 10 минут, допускает пять неверных попыток и используется один раз. Повторная отправка — не чаще раза в минуту, старый код заменяется. При повторной регистрации неподтверждённого адреса можно заново задать имя/пароль и получить новый код; уже подтверждённый аккаунт так изменить нельзя.

В локальный `.env` добавьте `RADAR_SMTP_USER` (полный адрес ящика Mail.ru) и `RADAR_SMTP_PASSWORD` (пароль внешнего приложения). Не отправляйте пароль в чат и не добавляйте в Git. Сервер по умолчанию — `smtp.mail.ru:465`, SSL/TLS с проверкой сертификата. После настройки выполните `docker compose up -d --wait`, чтобы API получил переменные. Инструкция Mail.ru: https://help.mail.ru/mail/login/mailer/.

Письмо отправляет сам backend стандартным Python `smtplib`; отдельного сервиса/очереди нет. Сетевой вызов вынесен в поток, чтобы не блокировать async API. В БД хранятся HMAC-хеш кода, срок, время отправки и счётчик попыток; ни API, ни логи код не раскрывают. Если SMTP не настроен или недоступен, регистрация возвращает понятную ошибку и не создаёт новый аккаунт. Существовавшие до изменения пользователи сохранены подтверждёнными.

Одна начальная Alembic revision создаёт сразу актуальную схему. Для существующей БД, где эта revision уже применена, её редактирование само по себе не добавляет поля: локальная рабочая БД обновлена отдельным `ALTER TABLE` после backup, без удаления данных.

## Устройство

```text
Browser → Next.js (SSR, формы, /api proxy) → FastAPI → PostgreSQL
                                             ↓
                                        gRPC Engine
                                             ↓
                                  HGB fit + NetCF forecast
```

- `backend/` — FastAPI, SQLAlchemy, проверки прав, импорт, агрегаты и gRPC-клиент. Единственная цепочка Alembic: `backend/alembic.ini` → `backend/migrations/versions/0001_initial_schema.py`, сразу создающая текущую схему. Новая БД разворачивается командой `upgrade head`; тест проверяет два цикла upgrade/downgrade в отдельной схеме тестовой БД.
- `frontend/` — Next.js App Router/TypeScript, серверное чтение данных и небольшие интерактивные формы.
- `contracts/forecast/v1/forecast.proto` — единственный исходник gRPC-контракта и сгенерированные Python-модули.
- `forecast_service/` — обучение `HistGradientBoostingRegressor` на истории одной компании внутри запроса.
- `tests/` — сквозные проверки; проверки отдельных модулей расположены рядом с ними.
- `scripts/` — локальный запуск, остановка и проверка.

Шесть таблиц: users, companies, memberships, invitations, categories, transactions. M:N реализована членством пользователя в компаниях. Роли owner/treasurer/viewer; владелец управляет участниками, owner/treasurer изменяют операции, все участники смотрят и запускают прогноз.

Приглашения сохраняют результаты: ожидание, принятие, отказ и отзыв. Просрочка вычисляется по сроку. В настройках → «Участники» владелец видит историю; продление отзывает прежнюю ссылку и создаёт новую на 48 часов. Получатель может принять или отклонить приглашение. Неизвестная дата создания прежних записей остаётся пустой. История миграций сведена к `0001_initial_schema`; downgrade до `base` удаляет всю прикладную схему и допустим только в одноразовой тестовой БД.

Деньги хранятся как положительный `Numeric(15,2)` и направление. REST передаёт суммы строками, gRPC — знаковые копейки int64. Импорт принимает только собственный CSV/XLSX-шаблон; предпросмотр не пишет данные, подтверждение сохраняет весь допустимый набор атомарно.

Для демонстрации можно создать **вымышленный** файл операций:

```powershell
uv venv --python 3.12 .venv
uv pip install --python .venv\Scripts\python.exe -r backend\requirements-dev.txt -r forecast_service\requirements-dev.txt
.venv\Scripts\python.exe scripts\generate-demo.py
```

Затем загрузить `artifacts/demo-transactions.csv` через экран импорта. Генератор не перезаписывает существующий файл: для повторного запуска передать новый `--output`. Это не финансовые данные реальной компании.

`scripts/python-local.ps1` запускает Python из корневой `.venv` с настройками `.env`, не выводя секреты. Его gRPC-порт по умолчанию **50052**, чтобы не конфликтовать с пользовательским Echo на 50051. Контейнеры обращаются к `forecast:50051` внутри своей сети, без публикации порта на хосте. Флаг `-TestDatabase` выбирает отдельную БД `${RADAR_DB_NAME}_test` (по умолчанию `cashflow_radar_test`), её нужно создать заранее; не направлять тесты со сбросом схемы на основную БД.

## Ограничения учебного примера

- Прогноз — NetCF, не остаток/прибыль/кассовый разрыв. Минимум 30 календарных дней — условие запуска, не гарантия качества; горизонт 7/30 дней. Пропуски от первой операции до выбранной отсечки считаются нулями.
- Случайный demo seed/тестовые платежи не являются исследовательскими данными. NetCF 54 SME в тысячах евро не импортируется как RUB-платежи.
- Нет дедупликации импорта: повторная загрузка создаёт повторные операции. После неизвестного сетевого исхода сначала проверить список.
- JWT без refresh/revocation и восстановления пароля. Почта подтверждается кодом при регистрации; приглашение передаётся доверенным каналом вручную. Ограничения кода действуют на адрес, общей антиспам-защиты по IP нет. Только локальный доверенный стенд.
- После изменений в другой вкладке обновите страницу и пересчитайте прогноз.

HTTP-приёмка: `.venv\Scripts\python.exe scripts\verify-http.py` (24 проверки).

Backend-тесты подменяют только отправку письма и проходят реальное подтверждение кода. HTTP/browser suites требуют `TEST_MAILBOX_URL` тестового почтового приёмника (GET с параметром `email`, ответ `{"code":"123456"}`). Этот endpoint не существует в основном API; не запускайте синтетические регистрации через настоящий ящик Mail.ru. Без тестового приёмника suites завершаются до отправки писем.

`tests/browser_email_verification.cjs` проверяет двухэтапную регистрацию в браузере: отсутствие сессии до кода, cooldown повторной отправки, ошибку неверного кода и вход после правильного. Запускается тем же Playwright wrapper с тестовым приёмником, что и остальные browser suites.
